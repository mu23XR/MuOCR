# MUOCR-006 — 旧版字体失败、缓存管理与简繁识别

Owner: Codex. Claimed: 2026-11-05. Status: completed for the requested bounded fixes; real user395-page PDF remains unverified.

后续MUOCR-007更正：0.1.3已内置同一中文字库；先前将该截图归因于“旧版依赖系统CJK、新版内置即可解决”不完整。实际普通样本字体/Unicode测试仍有效，但本地1.1.7按整行选字体，缺少上游新加的逐字混排回退，不能把用户原395页字体故障认定为已修。

用户提供0.1.3截图：第293/395页写入文字层时缺少可嵌入中文字体；OCR页已缓存但无法手动清理；“选择题”被识别为“选择題 ”。用户要求核对既有修复，继续解决遗漏并保证覆盖升级后的缓存交接。

开工 main `7a75f2b`，工作区干净。仅修改MuOCR，不操作GitHub或MuNote，不卸载/清除既有应用数据。模拟器仅原有1号，禁止0号与新建实例。

计划：核对0.1.3与当前字体/缓存格式；基线88项；保留原始识别/断点，设计明确可控的简体输出；提供缓存路径/大小/页数及有确认和并发保护的手动清理；验证旧格式缓存迁移及签名覆盖升级；运行JVM、生产构建和1号实例验收。清理不得删除源PDF或已导出的文件，失败必须明确报告。

证据、实现决定和测试结果分阶段追加。真实用户395页PDF未提供，不能声称复现该完整文件。

## 诊断与方案

- JVM基线88/88通过（`.tools/muocr006-baseline.log`）。
- 上游 `3f399670c079115f1006c88a22ebc81a9c73875b` 确认为0.1.3/code4，同包名及原公开测试签名。该版本逐页JSON仍是width/height/lines及5列行，当前读取兼容；旧目录为muocr-work/URI+size+modified的SHA256前16字节十六进制，当前迁移只扫一个存储根、复制失败被吞且中断后可能只导入部分页，需修。
- 截图提示找不到能覆盖该行的可嵌入字体。0.1.3本已有内置TrueType字库，本地沿用；本轮补针对“选择题/选择題”的普通字体/输出验收，不证明原混排失败行已修，也不声称所有稀有字均有字形。
- 用Android已有ICU提供可关闭的简体文字层，转换发生在导出时，不更改原始OCR页缓存。默认新任务简体，旧队列缺字段保持原始模式；旧0.1.3页导入新任务使用新任务所选模式。导出侧记录文字模式，模式不符重建文字层但保留OCR页。尾部Unicode空白统一处理，内部英文空格保留。Android官方要求先检查Transliterator可用ID；缺失明确报错，不静默替代。
- 缓存页显示按目录页记录计数，与旧截图的“写入第293页”分开；后者不是已缓存页数。扫描内外部两处muocr-work，清理仅限白名单子目录，阻止符号链接/越界；运行期和待核对输出禁止清理，失败保留清理标记，避免把残留当完整缓存续用。源文件和输出文档不进入删除范围。

## 最终实现与验证

- 新任务默认简体，旧队列缺字段保留原文。新增闲置任务「改为简体／改为原文」，要求未运行且没有待核对输出，受清理租约约束；选项变化保留OCR页，按需重建文字层。实际任务15切为原文、强停重开仍保持，再切简体完成导出。
- 手动清理先持久化discardLegacyCache再删除，防止重试从残留旧缓存复活已放弃的页；删除失败保留cleanup.pending。目录边界与故障、迁移中断、队列兼容/清理互斥、导出模式切换均有回归。取消/移除的私有缓存错误不再静默吞掉；SAF目标删除失败的持久URI追踪仍是R3剩余项。
